## Goal

Workflows can write PostGear content the same way a person does in the composer:

- **Create Draft** (P0) puts text, media and channels into Drafts; the draft opens in the composer like any other.
- **Add To Queue** (P1) schedules a post at the channel's next free posting time, or at a chosen time.
- **Publish To {Platform}** (P1) publishes now, one library card per platform, each listing only that platform's connected channels.
- **Get Post** (P1) loads a post by id (usually the trigger's post) so later steps can use its text, media and channels.

None of them hand-duplicates the composer's validation, and none can create the same post twice for one run, even when Temporal retries the activity.

## The Decision: How The Worker Creates Posts

The sprint doc forbids hand-copying validation into the worker. Creating a post today needs `ChannelsService.list`, `TagsService.findLive`, `MediaService.findViews`, the provider `manager` (for `rules`), `PostsRepository.createGroup`, and `SchedulingService` (for queue and publish-now). That is half the API's dependency graph.

| Option | What it means | Cost | Risk |
|---|---|---|---|
| A. Shared post-writer package | Move `prepare`, `assertQueueable`, `createGroup` and their lookups into a package both API and worker import | Large refactor of a Sprint 4/5 path that works; the worker gains Temporal-client duties it does not have today | Drift during the move; two callers to keep in step; touches the composer's hot path |
| **B. Internal step gateway (recommended)** | The worker calls a small set of API routes under `/internal/automation/*` with a service token. The API runs the real `PostsService` (and later `AiService`, `MediaService`, `MailService`) unchanged | One guard, one controller, one idempotency table | The worker depends on the API being up: handled because the activity retries on network and 5xx (`retry: 'transient'`) |

**Recommend B.** Reasons: zero duplication (the exact code path the composer and the copilot use), every future PostGear-domain step (AI in Module 11, Email in Module 12, Render Design in Module 15) reuses the same gateway, and the risk is a retry, which Temporal already handles. **The session must confirm this by reading the code above before building**: if `PostsService` turns out to be cheap to call outside Nest, say so in the decision log and pick A instead.

### Gateway design (built in this module, reused by 11, 12 and 15)

- **Env**: `AUTOMATION_INTERNAL_TOKEN` (64 hex chars, in both the API and worker env schemas, documented in `.env.example`, generated by `npm run generate:keys` if that script makes keys; refuse to boot the worker without it once any gateway step is executable). `API_URL` already exists in the worker env.
- **Guard**: `InternalTokenGuard` compares `X-PostGear-Internal` with `safeCompare` from `packages/db/src/crypto.ts`. Routes are `@Public()` (no user session) plus this guard, `@SkipThrottle()` is **not** used (keep the global throttle; the worker's concurrency is far below it).
- **Binding to a real run**: every request body carries `{ runId, nodeKey, organizationId }`. The API loads the `AutomationRun`, checks it belongs to that workspace, is `RUNNING` (or `WAITING` for review resumes), and that `nodeKey` exists in its pinned version's graph with the expected `type`. Anything else is a 404. A leaked token alone therefore cannot write into a workspace without a live run.
- **Idempotency table** (with the `prisma-change` skill): `AutomationEffect { id, organizationId, idempotencyKey String @unique, kind String, status ('PENDING' | 'DONE' | 'FAILED'), result Json?, createdAt, updatedAt }`. The key is `${runId}:${nodeKey}` (Module 07's convention).
  - First call inserts `PENDING`, does the work, stores `DONE` plus the result.
  - A retry finding `DONE` returns the stored result without acting.
  - A retry finding `PENDING` younger than 2 minutes answers 409 `in_progress` (the worker treats it as retryable); older than 2 minutes is treated as a crashed attempt and re-run, which is safe because the deterministic group id below makes the post write itself idempotent.
  - The maintenance workflow prunes effects older than 30 days with their runs.
- **Deterministic group**: the gateway passes a `group` derived from the idempotency key (UUID v5 over a fixed namespace) into a new optional `group` parameter of `PostsService.create` (internal callers only; the public DTO does not accept it). Before writing, `create` returns the existing group if rows with that group already exist. Two guards, one per layer.
- **Origin**: add `AUTOMATION` to `enum CreationMethod` and thread a `creationMethod` option through `createGroup` (today hard-coded `'WEB'`). The composer and Queue can later show "Created by a workflow".

Worker side: `apps/worker/src/automation/gateway-client.ts` with `callGateway(path, body)`, a 60 s timeout, and outcome mapping: 2xx returns the result, 409 `in_progress`, 408, 429 and 5xx are retryable, 400 and 422 fail the step with the API's message (already plain words, for example "Instagram (Bloom Bakery): Add at least one image."), 401 and 404 fail with "This step could not be authorised." and a security log line.

## Design: The Steps

### Create Draft (`postgear.createDraft`, P0)

Config (`.strict()`):

```ts
{ channels: string[] /* 1..20 channel ids */, text: string /* template */, media: string /* template, resolves to media refs */,
  tags?: string[], parts?: 'single' | 'splitOnBlankLines' }
```

- **Setup tab**: the shared channel picker (connected channels only, avatars).
- **Configure tab**: Text (multi-line chip input), Media (chip input that accepts media references from upstream, for example Generate Image's `image`, or a picker from the Media library), Tags, and "Make a thread from blank lines" (`splitOnBlankLines`).
- Execution: resolve tokens, turn each part into a document with `documentFromText`, media references into `{ id }`, then gateway `POST /internal/automation/posts/draft`, which calls `PostsService.create({ state: 'DRAFT', publishDate: nextFullHour(), ... })` (copy `nextFullHour` usage from the copilot tool; move it to a shared helper if it is private there).
- Output: `{ postGroup, link /* /[orgId]/... composer link */, channels: [{ id, name, provider }], text, mediaCount }`.
- Drafts skip queue rules (the composer does too); a draft never fails on platform limits. That matches `prepare()`, which only runs `assertQueueable` for the queue.
- **Dry run** (TEST mode, side effect `internal`): Module 07 decides whether `internal` steps run in tests. Recommended: Create Draft **does** run in tests (a draft is harmless and the user wants to see it, Journey B step 5) but the output carries `test: true` and the draft text is prefixed with nothing; instead the step's output says "Draft created from a test run." If the user prefers otherwise, flip the catalog flag, not code.

### Add To Queue (`postgear.addToQueue`, P1)

Config: `{ channels, text, media, tags?, when: 'nextSlot' | 'at', at?: string /* template or ISO */, timeZone: string }`.

- `nextSlot`: the first posting time (from `Integration.postingTimes`, minutes since local midnight) that is later than now plus 5 minutes and has no queued post on that channel within 1 minute of it. Interpreted in `config.timeZone` (an IANA zone defaulted from the browser, like the Schedule step; record in the decision log). Implement as a pure function `nextFreeSlot({ postingTimes, taken: Date[], from: Date, timeZone })` in the API next to the posts module, unit tested across a day boundary and DST.
- Runs through `PostsService.create({ state: 'QUEUE', publishDate })`, so `assertQueueable` applies every platform rule. A rule failure fails the step with the API's sentence. It is a permanent failure (not retried).
- Output: `{ postGroup, scheduledFor, channels }`.
- **Dry run**: "Would add to the queue for Instagram on Mon 3 Nov at 09:00: {first 80 characters}". Runs for real only with the step's "Send for real in tests".

### Publish To {Platform} (`postgear.publish`, P1, `publishes: true`)

- One type; `config.provider` fixes the card. The library shows one card per platform in **Social Channels** (Instagram, Facebook, X, LinkedIn, YouTube, TikTok, Pinterest), each listing only that platform's connected channels; a platform with none shows **Needs Connection** with "Connect a channel" linking to the Channels page.
- Config: `{ provider, channels /* of that provider only, validated */, text, media, settings?: Record<string, unknown> /* provider settings form from settingsFieldsFor(provider) */ }`.
- Execution never calls a provider. It creates the post through `PostsService.create({ state: 'QUEUE', publishNow: true })`, which writes the rows and signals `publishNow` through the existing `postPublishWorkflow`. Retries, `[simulate:...]` markers, failure reasons and the Post Failed trigger all keep working because it is the same path.
- Output: `{ postGroup, channels, status: 'publishing' }`. The step does not wait for the platform (publishing can take minutes); a following step that needs the URL should use a separate workflow on **Post Published**. The panel says so in one sentence.
- **Dry run**: "Would publish to Instagram (Bloom Bakery) now: {first 80 characters}".
- **Activation**: `riskSummary` (Module 02) already marks `publishes`. Confirm the dialog shows the extra tick when no Manual Review is upstream.
- **Never twice**: the gateway effect row plus the deterministic group. Add a worker test that replays the activity after the first call succeeded.

### Get Post (`postgear.getPost`, P1)

- Config: `{ post: string /* template, usually {{ trigger.post.id }} */ }`.
- Gateway `POST /internal/automation/posts/get` returns a redacted summary through `PostsService.get`: `{ id, group, state, text, mediaCount, media: [{ id, url, type }], channels, tags, publishDate, releaseUrl }`. Read-only, `sideEffect: 'none'`, runs in tests.
- Missing or another workspace's post: "This post no longer exists." (permanent).

### Media references between steps

Define once in `packages/automation` (Module 02 output types): `MediaRef = { kind: 'media', id: string, url?: string, type: 'image' | 'video' }`. Generate Image (Module 11) outputs `image: MediaRef`; Create Draft's Media field accepts `MediaRef | MediaRef[]`. A chip that resolves to anything else fails the step with "The media field needs an image or video from an earlier step."

## Tests

- Gateway guard: no token 401, wrong token 401, right token but foreign run 404, finished run 404, node key not in the version 404.
- Effect claim: first call acts; second returns the stored result; concurrent `PENDING` answers 409; stale `PENDING` re-runs and finds the existing group.
- `PostsService.create` with a known group returns the existing post (no second row).
- Create Draft: a thread from blank lines; media from a `MediaRef`; a foreign media id is refused with the posts message.
- Add To Queue: next slot across midnight and DST; a platform rule failure fails the step permanently.
- Publish: worker replay test (activity retried after success) creates one post and one publish signal.
- Executors' dry runs return the "Would ..." sentences and call no gateway route.
